# v0.2.0: the document model and store

Measured on 2026-11-08 on main after #33 and #34, before the class
version column and the terminal check of #35 joined the commit, with Go
1.26.9, linux/amd64, on an Intel Core Ultra 9 275HX with 24 threads and
31 GB available to the Linux VM (WSL2, kernel 6.18), the database files
on the virtual disk that holds the home directory, ext4 on a VHD on NVMe,
where an fsync of 4 KB costs 4.0 ms at the median. The in-memory
benchmarks are the mean of three runs; the campaigns run once and report
percentiles. The budgets are those of
[ADR-0012](../adr/0012-performance-gates.md).

The five-operation arithmetic formula of v0.1.0 is unchanged at 13.7 ns;
the gate watches it on every pull request. The set-wise recompute, the
mining view and the browser VM budgets wait for Phases 7 and 8.

## Recalculation

| Benchmark | What | Time | Allocations |
|---|---|---|---|
| Recalculate | the four auto formulas and the title of the test invoice class | 162 ns | 3, 64 B: the text concatenations of two formulas |
| Recalculate50 | fifty chained auto formulas over ten inputs | 1.3 µs | 0 |
| LookupIndexed | one indexed lookup and one arithmetic formula | 88 ns | 0 |
| LookupKeyedStatement | the same through the statement, above `MaxIndexedRows` | 2.4 µs | 34, 1.4 KB |
| LookupStatement | a lookup with an AND condition, the condition over 1,000 rows | 35 µs | 30, 1.3 KB |

The recalculation itself allocates nothing: the dirty flags, the slot
buffer and the VM are reused under the writer's lock. What allocates is
a formula whose result is text, and the statement paths' database/sql
boxing.

## The filter

A class with an indexed text variable and two plain ones, filtered after a
load of one commit per document (ADR-0038); medians of twenty runs,
compiling the filter and building the documents included:

| Filter | 100,000 documents | 1,000,000 documents |
|---|---|---|
| `number = "T-…"`, indexed, one document | 88 µs | 54 µs |
| `number >= "T-…" AND number < "T-…"`, indexed range, ten documents | 59 µs | 56 µs |
| `priority = 3 AND owner = "u7"`, plain columns, first ten | 0.62 ms | 0.53 ms |
| `Count` of `priority = 3`, a plain column, the whole table | 19.8 ms | 57.9 ms |

The last row is a full scan and grows with the table; `"index": true` on
the column is the answer. The million documents loaded one commit each
in 77 s.

## The commit campaign

`TestCommitCampaign` in the store package runs the real commit on the
test invoice class: twenty inputs of every stored kind, two vocabulary
objects flattened to prefixed columns, a `rows` variable of three lines
and an `array` of two tags carried forward per version, four auto
formulas and a title; the `Order` class adds one indexed lookup, one
statement lookup and a lookup in a default. One transaction per commit
unless the row says batched; the latency of a batch is the batch's.

One million commits of each kind, in order, into one database; the WAL is
truncated past 64 MB, the default:

| Work | Commits | Throughput | p50 | p90 | p99 | max |
|---|---|---|---|---|---|---|
| create, one transaction each | 1,000,000 | 9,929/s | 0.078 ms | 0.106 ms | 0.187 ms | 535 ms |
| set, one transaction each, no key | 1,000,000 | 7,779/s | 0.105 ms | 0.146 ms | 0.261 ms | 733 ms |
| set, one transaction each, with a key | 1,000,000 | 7,135/s | 0.113 ms | 0.162 ms | 0.315 ms | 736 ms |
| preview of that set | 1,000,000 | 43,754/s | 0.021 ms | 0.025 ms | 0.041 ms | 4.91 ms |
| create, batched 1,000 per transaction | 1,000,000 | 24,149/s | 39.1 ms | 40.6 ms | 58.8 ms | 224 ms |
| set with two lookups recomputed | 1,000,000 | 10,820/s | 0.069 ms | 0.101 ms | 0.186 ms | 735 ms |

Afterwards the Invoice class holds 2,000,000 documents with 3,000,000
history rows, the file is 6.7 GB and opening it takes 1.6 ms.

What the rows say. A commit costs about 80 µs at the median, of which the
write step alone measured 60 to 70 µs in ADR-0035, so the compute, the
read of the current row, the checks and the two child tables carried
forward cost 10 to 20 µs. The key of ADR-0026 costs one indexed lookup
before the compute, 8 µs at the median and 8 percent of throughput. A
preview is the commit without the write, 21 µs: the budget of ADR-0025,
"a commit without the fsync", holds with the write at a quarter of the
commit. The two lookups of the Order class, one from the index and one
through a statement, add nothing visible: the Order row is faster than
the Invoice rows because the class is smaller. Batching pays the
transaction once per thousand documents and reaches two and a half times
the budget.

The maximum of every unbatched row, 0.3 to 0.7 s, is the truncating
checkpoint of ADR-0035 item 7: once the log passes its limit the
checkpointer copies it into the database file, fsyncs it and empties it,
and the writer waits for the copy. It is one commit in tens of thousands
and does not reach p99. The record asked for the limit to be measured
with the real commit; at 100,000 commits with the log truncated past
16, 64 and 256 MB the pause stayed between 0.25 and 0.5 s and p99 moved
within noise, so the pause is the fsync of a large database file and not
the size of the log, and 64 MB stays. A writer that must never wait that
long runs its checkpointer with a smaller limit and `synchronous=FULL`
is unaffected, since every commit fsyncs anyway; both are the embedder's
options.

## The three evaluators

The conformance suite holds 1,274 evaluation cases in 16 suites, 137
accepted and 87 rejected syntax cases, and 180 accepted and 165 rejected
binding cases in 7 suites. Every evaluation case passes exactly on the Go
VM, on SQLite through modernc.org/sqlite and on DuckDB through the
`analytics/` module, the `lookup` suite included, whose tables the VM
reads from an in-memory executor and the SQL dialects from tables created
in the database.

- [ADR-0038](../adr/0038-the-filter-and-the-read-only-sql-endpoint.md):
