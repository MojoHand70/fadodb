# v0.3.0: the statechart, the rights and the chosen moment

Measured on 2026-11-09 on main after #44, with Go 1.26.9, linux/amd64,
on an Intel Core Ultra 9 275HX with 24 threads and 31 GB available to
the Linux VM (WSL2, kernel 6.18), the database files on the virtual disk
that holds the home directory, ext4 on a VHD on NVMe, where an fsync of
4 KB costs 0.5 ms at the median and 1.3 ms at p90, measured with
200 writes and fsyncs of one block from Python. The in-memory benchmarks are the
mean of three runs; the campaigns run once and report percentiles. The
budgets are those of [ADR-0040](../adr/0040-transitions-as-commits.md),
[ADR-0041](../adr/0041-field-rights-and-transition-rules-in-the-go-api.md)
and [ADR-0042](../adr/0042-a-moment-the-caller-chooses.md), with the
Phase 2 rows of [v0.2.0](v0.2.0.md) run again on the same build.

## The statechart

| Benchmark | What | Time | Allocations |
|---|---|---|---|
| Transition | one named transition with a guard, write and event, the database on tmpfs | 61 µs | 168, 8.2 KB |
| TransitionChain | a named transition and one eventless hop per cycle | 60 µs | 189, 9.3 KB |
| Transitions | the listing of three candidates, guards evaluated | 5.5 µs | 69, 3.1 KB |
| Transitions10 | the listing of ten candidates | 5.7 µs | 68, 3.7 KB |
| GuardLoop | the six guards of the `Flow` class over a row | 34.6 ns | 0 |
| Recalculate50 | fifty chained auto formulas over ten inputs, as in v0.2.0 | 1.36 µs | 0 |

The compute of a transition is its guard, a few tens of nanoseconds; what
a transition commit costs beyond a set is nothing, and the chain's hop
is one more history row in the same transaction. What the listing pays
is the read of the row from SQLite on the writer's connection, 3 KB and
68 allocations of database/sql boxing; ten guards add 0.2 µs to three.
The hot paths allocate nothing: the guard loop, the chain's walk over
the states and the write check reuse the writer's buffers, as the
recalculation does.

## The rights

| Benchmark | What | Time | Allocations |
|---|---|---|---|
| Project | fifty variables with a rights cell each, 25 group lists and 25 formulas over the document, for a principal the lists name | 1.7 µs | 0 |
| WriteCheck | ten variables set under group lists and formulas, over the stored document | 0.28 µs | 0 |
| Compile | the filter compiler on an indexed equality, plain / with a formula read right | 3.6 / 3.8 µs | 87 / 92, 6.4 / 6.8 KB |

The projection evaluates 25 formulas and 25 group tests in a third of
its budget and allocates nothing: the rights table is resolved per state
when the class is laid out, the read paths borrow an evaluator from a
pool, and a hidden variable is a map delete. The write check finds the
set variables by their declared names and evaluates their rights alone.
The compiler keeps each class's read rights ready, so a filter that names
a guarded variable pays 0.2 µs and five allocations for the predicate's
text.

## The filter

The class of v0.2.0, an indexed text variable and two plain ones, and
`Guarded`, the same class with the read right
`INGROUP("support") OR owner = USER()` on the indexed variable, filtered
as a principal in the group, after a load of one commit per document; the
filter's prepared statements are cached since #43. Means over the
benchmark's runs, compiling the filter, binding the principal and
building the documents included:

| Filter | 100,000 documents | 1,000,000 documents |
|---|---|---|
| `number = "T-…"`, indexed, one document | 14.5 µs | 15.1 µs |
| the same with the read right on `number` | 15.1 µs, +4.5% | 15.1 µs, +0.1% |
| `number >= "T-…" AND number < "T-…"`, indexed range, ten documents | 34.0 µs | 34.2 µs |
| the same with the read right on `number` | 36.8 µs, +8.3% | 36.3 µs, +6.0% |
| `priority = 3 AND owner = "u7"`, plain columns, first ten | 0.50 ms | 0.50 ms |
| `Count` of `priority = 3`, a plain column, the whole table | 6.3 ms | 65.2 ms |

The indexed filters run in a quarter of their v0.2.0 time, 54 µs then
and 15 µs now for an equality over a million documents: SQLite's parse,
half of a filter's time, is paid once per statement text since #43
cached the prepared statements, and the first run of a filter still pays
it. A formula read right that reads the principal costs the bind of two
parameters and the predicate on each row the index yields, under a
microsecond on one document and 2 to 3 µs on ten, within the 15% the
amended record allows; a group list costs the compiler's bookkeeping
alone. The full scan of the last row grows with the table, as it did:
`"index": true` on the column is the answer.

## The commit campaign

`TestCommitCampaign` in the store package runs the real commit on the
test invoice class of v0.2.0, and now on three statechart classes: `Flow`,
five states and six transitions, where every command is a named
transition with a guard, `submit` then `back` on each document in turn so
that no eventless transition follows; `Chain`, six states, where every
command is a named transition followed by two eventless ones, three
versions, three history rows and three events in one transaction; and
`Hub`, one working state with ten named transitions leaving it, each with
a guard of its own, comparisons, `INGROUP`, `USER()`, `TODAY()`, text
and arithmetic among them. One transaction per commit unless the row
says batched; the listing writes nothing.

One million commits of each kind, in order, into one database; the WAL is
truncated past 64 MB, the default:

| Work | Commits | Throughput | p50 | p90 | p99 | max |
|---|---|---|---|---|---|---|
| create, one transaction each | 1,000,000 | 7,856/s | 0.089 ms | 0.139 ms | 0.337 ms | 938 ms |
| set, one transaction each, no key | 1,000,000 | 6,292/s | 0.121 ms | 0.197 ms | 0.448 ms | 736 ms |
| set, one transaction each, with a key | 1,000,000 | 5,896/s | 0.123 ms | 0.200 ms | 0.474 ms | 836 ms |
| preview of that set | 1,000,000 | 36,317/s | 0.024 ms | 0.032 ms | 0.093 ms | 9.24 ms |
| preview of that set at a chosen moment | 1,000,000 | 37,157/s | 0.024 ms | 0.031 ms | 0.089 ms | 2.63 ms |
| create, batched 1,000 per transaction | 1,000,000 | 21,494/s | 44.5 ms | 46.8 ms | 63.6 ms | 228 ms |
| set with two lookups recomputed | 1,000,000 | 8,968/s | 0.079 ms | 0.129 ms | 0.333 ms | 636 ms |
| transition, one transaction each | 1,000,000 | 10,173/s | 0.063 ms | 0.108 ms | 0.280 ms | 1,280 ms |
| transition with values | 1,000,000 | 10,656/s | 0.065 ms | 0.114 ms | 0.291 ms | 635 ms |
| transition starting a chain of three | 1,000,000 | 7,217/s | 0.106 ms | 0.166 ms | 0.395 ms | 735 ms |
| listing of ten candidate transitions | 1,000,000 | 179,813/s | 0.005 ms | 0.006 ms | 0.017 ms | 4.80 ms |

Afterwards the Invoice class holds 2,000,000 documents, the file is
10.1 GB and opening it takes 3.1 ms.

What the rows say. A transition commit costs 63 µs at the median, less
than a set on the invoice class because the `Flow` class is smaller: two
history columns fewer, no composites to carry forward, one guard to
evaluate. Values on the transition add 2 µs, the assignment and the
recalculation they trigger. The chain of three writes three versions and
three events for 106 µs, 1.7 times one transition and well within the
three plain writes the record allows, since the three history rows share
one transaction and one fsync. The listing of ten candidates evaluates
ten guards over the stored row for 5 µs at the median and 17 µs at p99,
on the writer's turn, with the row read from SQLite inside that; the
budget of 10 µs holds at the median and the guard loop itself is 35 ns
for the six guards of `Flow` (`BenchmarkGuardLoop`, below). A preview at a
chosen moment costs the same as a preview at the clock, 24 µs, as
ADR-0042 said it would: the option sets the `Now` of a context every call
fills already.

The Phase 2 rows run 15 to 20 percent slower than in v0.2.0 on this day:
7,856 creates per second against 9,929, a set at 0.121 ms against
0.105 ms at the median. Between the two measurements the commit gained
the class version column and the terminal check of #35, the rights and
the clock of Phase 3, each a branch on an empty table for a class without
rights, and the day's disk: the maxima, which are the truncating
checkpoint of ADR-0035, are higher too. Every Phase 2 budget still holds
with room, p99 under half a millisecond against two.

## The three evaluators

The conformance suite holds 1,289 evaluation cases in 16 suites, 141
accepted and 89 rejected syntax cases, and 182 accepted and 170 rejected
binding cases in 7 suites; every evaluation case passes exactly on the Go
VM, on SQLite through modernc.org/sqlite and on DuckDB through the
`analytics/` module. New in Phase 3 are the statechart suites under
`conformance/statechart/`, scripts the store runs against a class with
their principals and, since ADR-0042, their clock: `approval`,
`eventless`, `stateless`, `rights` and `clock`, 85 steps in all, the
specification of ADR-0040, ADR-0041 and ADR-0042 for the server and the
browser VM to run with their phases.

## What the records measured on the way

- [ADR-0040](../adr/0040-transitions-as-commits.md): the first
  implementation, #42, measured a transition commit at 60 µs, a chain
  at 56 µs and the listing of three candidates at 5 µs on tmpfs, the guard
  loop at 34 ns without an allocation, before the campaign above ran them
  on disk.
- [ADR-0041](../adr/0041-field-rights-and-transition-rules-in-the-go-api.md):
  the read right compiled into a filter, measured by shape in #43 against
  a plain indexed filter of 12.9 µs with cached statements: a group list
  0.44 µs, a formula without parameters 0.6 µs, `owner = USER()` 0.83 µs,
  `INGROUP("support")` 1.1 µs, both 1.35 µs; the finding that half of an
  indexed filter's time was SQLite's parse, which the statement cache
  removed and which halved the plain filter; and the finding that
  `INGROUP` as a `json_each` subquery cost a microsecond per statement
  run, which the delimited groups and `instr` removed. The record's filter
  budget was amended on those numbers.
- [ADR-0042](../adr/0042-a-moment-the-caller-chooses.md): nothing to
  measure, and the preview rows above show it.
