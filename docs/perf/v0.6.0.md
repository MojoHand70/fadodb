# v0.6.0: the server

Measured on 2026-11-16 on main after the last pull request of the
phase's measuring (`f58ebec`), with Go 1.26.11, linux/amd64 and SQLite
1.62.0, on an Intel Core Ultra 9 275HX with 24 threads and 31 GB
available to the Linux VM (WSL2, kernel 6.18), the database files on
the virtual disk that holds the home directory, ext4 on a VHD on NVMe.
An fsync of 4 KB cost 4.0 ms at the median and 4.4 ms at p90 when the
run began, measured with 200 writes and fsyncs of one block from
Python; two hours earlier the same evening it cost 1.4 ms and 2.2 ms,
and on the day of [v0.5.0](v0.5.0.md) 1.0 ms and 1.2 ms. A commit does
not wait for the disk unless the database was created with `FULL`, so
the rows of the campaigns stand beside those of the earlier releases.
The in-memory benchmarks are the mean of three runs; the campaigns ran
once and report percentiles; the campaign of the stream ran four times
and the slowest run is here. The budgets are those of
[ADR-0011](../adr/0011-one-json-command-set.md),
[ADR-0055](../adr/0055-the-command-set-on-the-wire.md),
[ADR-0057](../adr/0057-users-groups-and-keys.md),
[ADR-0058](../adr/0058-the-stream-of-changes.md) and
[ADR-0065](../adr/0065-a-way-in-for-messages-from-outside.md), with the
rows of Phases 2 to 5 run again on the same build.

Every budget holds, the server's as
[ADR-0066](../adr/0066-what-the-servers-budget-is-measured-beside.md)
measures it. ADR-0011 gives the server 200 µs at p99 beyond
a transition over the Go API. Beside the Go API in a loop the server
takes 0.33 ms more, most of which this machine takes for any request.
Beside the same transition made through the Go API by a plain server
that was sent a request for it, the server adds nothing that can be
told from the noise. [The server](#the-server) sets the numbers out.

**Corrected on 2026-11-17.** This page first said that 0.155 ms of a
transition through the server were the server's own. That figure came
from a comparison that did not repeat and was not the server's; the

counted the memory of an open database wrongly. It had not: that

The measuring found three things in the engine, and each was mended

## The server

`TestServeCampaign`: one database on disk, served by `fadodb serve` as
it is told nothing but where its database is, and 200,000 calls a row.
One caller on one connection that is kept open, unless the row says
otherwise. The same calls are made first through the Go API and as
commands on the same database, and a request that does nothing is sent
to a server of Go's own that knows nothing of FadoDB.

| Work | Throughput | p50 | p90 | p99 | max |
|---|---|---|---|---|---|
| transition, the Go API | 14,276/s | 0.055 ms | 0.082 ms | 0.214 ms | 77.0 ms |
| read by id, the Go API | 166,086/s | 0.005 ms | 0.006 ms | 0.018 ms | 0.52 ms |
| transition, as a command | 13,984/s | 0.056 ms | 0.082 ms | 0.229 ms | 75.7 ms |
| read by id, as a command | 142,801/s | 0.006 ms | 0.007 ms | 0.027 ms | 0.40 ms |
| a request that does nothing, Go's own server on this machine | 6,377/s | 0.149 ms | 0.197 ms | 0.321 ms | 2.26 ms |
| `whoami`, through the server | 5,849/s | 0.164 ms | 0.207 ms | 0.336 ms | 19.3 ms |
| read by id, through the server | 4,641/s | 0.208 ms | 0.250 ms | 0.397 ms | 36.8 ms |
| transition, through the server | 2,892/s | 0.318 ms | 0.377 ms | 0.546 ms | 39.0 ms |
| read by id, through the server, sixteen callers | 45,641/s | 0.318 ms | 0.431 ms | 0.699 ms | 66.3 ms |
| transition, through the server, sixteen callers | 10,162/s | 1.473 ms | 1.852 ms | 2.836 ms | 64.8 ms |

- **A transition through the server takes 0.318 ms at the median and
  0.546 ms at p99**, where the Go API in a loop takes 0.055 ms and
  0.214 ms: 0.263 ms and 0.332 ms more.
- **This machine takes more than the budget for a request that does
  nothing.** Go's own server answers one in 0.149 ms at the median and
  0.321 ms at p99: the loopback of the virtual machine and Go's HTTP,
  with no FadoDB in them.
- **Without a network the door adds 7.7 µs** to its command, and the
  command nothing that can be told from the noise of a commit
  (`BenchmarkDoorTransition`, `BenchmarkExecTransition`,
  `BenchmarkTransition`).
- **What the server adds over the network was measured again**, beside
  a program that makes the same transition through the Go API when it
  is sent a request: [the budget, measured again](#the-budget-measured-again).
- **`whoami` shows the least a request costs through the server**:
  0.164 ms, 0.015 ms more than a request to Go's own server.
- **Sixteen callers that write wait for each other**: one commit runs
  at a time, so a transition takes 1.47 ms at the median while the
  server makes 10,162 a second, three and a half times what one caller
  gets through it.
- **Sixteen callers that read do not**: 45,641 reads a second, ten
  times one caller's, at 0.70 ms at p99. Before the mend of the
  reading connections it was 11,885 a second and 18.4 ms at p99.

### The budget, measured again

On 2026-11-17, on main at `bc4de71` with the campaign of
[ADR-0066](../adr/0066-what-the-servers-budget-is-measured-beside.md):
three runs of `TestServeCampaign`, 200,000 calls a row. The second row
is new. A server of Go's standard library, with nothing of FadoDB's
server in it, is sent the same request, makes the transition through
the Go API and answers `{}`.

| Work, median and p99 | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| a request that does nothing, Go's own server | 0.148 ms, 0.243 ms | 0.164 ms, 0.312 ms | 0.165 ms, 0.324 ms |
| transition, the Go API called by a request to Go's own server | 0.336 ms, 0.581 ms | 0.353 ms, 0.628 ms | 0.351 ms, 0.625 ms |
| transition, through `fadodb serve` | 0.310 ms, 0.523 ms | 0.296 ms, 0.547 ms | 0.340 ms, 0.601 ms |
| what the server adds | -0.026 ms, -0.057 ms | -0.057 ms, -0.080 ms | -0.012 ms, -0.024 ms |
| for comparison, transition, the Go API in a loop | 0.054 ms, 0.207 ms | 0.055 ms, 0.207 ms | 0.055 ms, 0.215 ms |

- **The server adds nothing that can be told from the noise.** It does
  all that the plain program does and more, and still came out quicker
  in the three runs, by up to 0.080 ms at p99. That much is the noise
  between two rows of one run on this machine, which are measured
  minutes apart. The budget is 0.200 ms.
- **A transition costs more inside a request than in a loop, whoever
  makes it.** A request that does nothing takes about 0.15 ms and a
  transition in a loop 0.055 ms; the two together take 0.34 ms, with
  no part of FadoDB's server in them. Where the rest goes was not
  measured.
- **What this page said before.** It compared the server with a request
  that kept Go's server busy for 0.053 ms and did nothing, and called
  the 0.155 ms between them the server's own. Measured twice more, the
  same comparison gave 0.227 ms and 0.195 ms. The figure was not the
  server's: a handler that spins does not cost what a commit costs
  inside a request. The row of that request is taken out of the table
  above; its numbers were 0.221 ms at the median and 0.391 ms at p99.

## The way in

The same campaign, with an inlet whose message makes a document: a
message of 2 KiB with a signature over a timestamp and its body, a
`when`, a `key` read from it and three values.

| Work | Throughput | p50 | p90 | p99 | max |
|---|---|---|---|---|---|
| a document made with a key, the Go API | 13,103/s | 0.059 ms | 0.089 ms | 0.210 ms | 89.1 ms |
| a message of 2 KiB that makes that document, the Go call | 8,178/s | 0.098 ms | 0.137 ms | 0.268 ms | 83.9 ms |
| the same messages again, the Go call | 14,311/s | 0.066 ms | 0.078 ms | 0.156 ms | 8.2 ms |
| a message of 2 KiB that makes a document, through the server | 2,467/s | 0.377 ms | 0.444 ms | 0.652 ms | 46.4 ms |
| the same messages again, through the server | 3,064/s | 0.315 ms | 0.370 ms | 0.504 ms | 128.6 ms |

- **What stands before the command costs 0.039 ms at the median on
  disk**, and 27 µs in memory: the secret read, the signature checked
  over 2 KiB, the user looked up and the formulas over the JSON of
  the message, five of them in the campaign and three in the
  benchmark. The budget of ADR-0065 is 100 µs.
- **Most of it is reading the JSON once for each formula.** A message
  parsed once for all its formulas would take less; that is not done.
- **A message sent again costs less than the first**, 0.066 ms: its
  proof is checked and its formulas are worked out, and the key finds
  the commit that was made. Before the mend of the repeated key it
  cost 1.1 ms with 25,000 events in the database, and grew with them.
- **Through the server a message costs what a transition does**, with
  2 KiB more to read: 0.377 ms. Its sender waits on the machine, as
  every caller does.

## Opening a database

`TestOpenCampaign`: a database of fifty classes, each with twelve
variables, four states, three transitions, a rule and its access
rules, and 200 documents a class; 10.4 MB on disk. It is opened twenty
times, and then fifty copies of it are held open at once.

| What | Measured |
|---|---|
| defining the fifty classes | 172 ms |
| opening it | 31.4 ms at the median, 32.5 ms the longest |
| closing it | 4.6 ms at the median |
| memory an open database holds, after a read and a commit | 23.4 MB as the system counts it, of which 2.0 MB are Go's own |
| open files it holds | 7 |
| goroutines it holds | 3 |
| what sixteen callers reading at once add to it, as they finish | 54.5 MB and 22 open files; it has 10 connections open |
| the same, 35 seconds after the last read | 44.8 MB and 15 open files; it has 3 connections open |

- **An open database holds about 1.5 MB, and 0.44 MB more for each
  class.** With fifty classes that is 23.4 MB, of which 2.0 MB are
  Go's own: SQLite's memory is not among what Go counts. The table
  below has it for four, twenty and fifty classes.
- **Opening costs 0.6 ms a class.** Fifty classes are 31 ms, inside
  the 50 ms that Phase 2 allows an open; a database of a hundred
  classes would not be.
- **Readers at once leave memory behind for as long as the database is
  open.** Each reader has a connection, of about 3.4 MB in this
  database of fifty classes and 0.5 MB in one of four. The engine
  closes the connections of readers that have gone, all but one, and
  the open files go with them; the memory mostly does not, while any
  connection of the database lives. It was so before this release too:
  with two connections kept for good, as the engine had it, the same
  sixteen readers leave 46.3 MB, then and 35 seconds later. Closing the
  database gives all of it back.
- **The first read after a quiet spell takes 0.1 ms**, on the one
  connection that is kept ready.

### By the number of classes

Measured on 2026-11-17, on main at `ade495d`: the same campaign with
`FADODB_BENCH_CLASSES` set to 4, 20 and 50, twice each, the larger of
the two. The databases of four classes were held open 300 at once, as
[ADR-0056](../adr/0056-one-database-for-each-customer.md) measured
them; the others 50 at once.

| Classes | Opening it, at the median | Memory an open one holds | of which Go's own | Sixteen readers at once add | The same, 35 seconds later |
|---|---|---|---|---|---|
| 4 | 3.3 ms | 3.2 MB | 0.22 MB | 8.4 MB | 6.5 MB |
| 20 | 12.0 ms | 10.3 MB | 0.84 MB | 24.3 MB | 20.1 MB |
| 50 | 31.0 ms | 23.4 MB | 2.00 MB | 54.7 MB | 45.4 MB |

- **ADR-0056's figure stands.** It measured 2.9 MB for a database of
  four classes that is held open; here it is 3.2 MB. A thousand such
  databases are about 3 GB, as that record says. A thousand of fifty
  classes would be 23 GB.
- **Memory and the time to open both grow in step with the classes**:
  0.44 MB and 0.6 ms for each.
- **So does what readers at once leave behind.** Where that memory
  goes was not measured.

## The stream

`TestStreamCampaign`, the rows of ADR-0058: each subscriber on a
connection of its own, the read rule asked for every event, 5,000
commits a row, four runs. The slowest run of each row:

| Subscribers | The writer | Commits/s | p50 | p99 | Longest |
|---|---|---|---|---|---|
| 1 | commits every millisecond | 681 to 699 | 0.25 ms | 0.52 ms | 1.7 ms |
| 100 | commits every millisecond | 777 to 778 | 0.71 ms | 2.03 ms | 7.3 ms |
| 1 | never pauses | 14,032 to 14,512 | 0.51 ms | 1.49 ms | 2.4 ms |
| 100 | never pauses | 6,636 to 7,932 | 4.12 ms | 16.68 ms | 28.8 ms |

The budget, 5 ms at p99 with a hundred subscribers, is for the writer
that commits every millisecond, and holds at 2.03 ms. A writer that
never pauses with a hundred subscribers is beyond it, as it was when
the stream was built: the entries of many commits then travel together,
and the writer loses up to half its commits a second to the readers.

## What the measuring found

Each was found by a row of these campaigns that was slower than it had
a reason to be, and was mended before the numbers above were taken.

- **A command sent again with its key searched the whole log.** It is
  answered with the last version its commit made, and the engine
  looked for that among every event of the database, inside the
  writer's turn: 2.4 ms beside 50,000 events, growing with them, while
  every other commit waited. It now reads the events of its own
  document: 0.022 ms. It had been so since a command could start a
  chain, in Phase 3, and showed when a message sent again took twelve
  times as long as the first.
- **Callers reading at once had their connections opened and closed
  over and over.** The store kept two connections ready, which is
  what Go's database library does when it is told nothing. Sixteen
  callers read fewer documents a second together than one alone, and
  one read in a hundred through the server took 18 ms. Eight are now
  kept ready.
- **That mend closed the last reading connection too**, after a
  quarter of a minute without a read, so that the first read after a
  quiet spell paid 5 ms for a connection. It was on main for 23
  minutes and in no release. One connection is now kept ready for
  good.
- **The measuring itself was wrong twice.** The campaign signed its
  messages when it began and sent them more than five minutes later,
  and the engine refused them as it should. And memory was first
  counted as Go's own, which leaves SQLite's out: the 2 MB of an open
  database are 23 MB.

## What is slow

- **A caller on this machine waits 0.3 ms for the server** where the
  Go API answers in 0.05 ms, and most of that is the machine's.
- **Callers that write at once wait for each other.** There is one
  writer at a time; sixteen get 10,000 commits a second through the
  server between them, each waiting 1.5 ms.
- **The stream falls behind a writer that never pauses** when a
  hundred subscribers listen: 16.7 ms at p99.
- **The flow of a class of a million documents takes four seconds**
  for a caller who reads them all.
- **Opening takes 0.6 ms a class.**
- **An open database of fifty classes holds 23 MB**, and about 45 MB
  more once many callers have read from it at once, until it is
  closed. One of four classes holds 3 MB, and 6 MB more.
