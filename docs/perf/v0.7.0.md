# v0.7.0: the browser VM, people and agents at the server

Measured on 2026-11-24 on main at `a162664`, the last pull request of
the phase's steps, with Go 1.26.11, linux/amd64 and SQLite 1.62.0, on
an Intel Core Ultra 9 275HX with 24 threads and 31 GB available to the
Linux VM (WSL2, kernel 6.18), the database files on the virtual disk
that holds the home directory, ext4 on a VHD on NVMe. The campaign of
the door for agents and the benchmarks of signing in are new; they ran
on the pull request that adds them, which changes no line of the
engine. An fsync of 4 KB cost 0.92 ms at the median when the run began
at 18:17, 3.88 ms at 19:24 and 3.94 ms when it ended at 20:15. A
commit does not wait for the disk unless the database was created with
`FULL`. The in-memory benchmarks are the mean of three runs. The
campaign of the server ran three times: its table is of the first, and
what the server adds is given for each. That of the stream ran four
times, and the slowest run of each row is here. The others ran once and
report percentiles. A demo that the owner uses served a database of
its own on the machine throughout. The budgets are those of
[ADR-0003](../adr/0003-bytecode-as-interchange-format.md),
[ADR-0029](../adr/0029-browser-vm-as-one-plain-javascript-file.md),
[ADR-0067](../adr/0067-the-log-of-reads.md),
[ADR-0072](../adr/0072-the-size-budget-of-the-core-program.md),
[ADR-0076](../adr/0076-a-value-worked-out-when-it-is-read.md) and
[ADR-0081](../adr/0081-functions-over-a-list.md), with the rows of
Phases 2 to 6 run again on the same build.

Every budget holds. Measured beside v0.6.0 the same evening, Phase 7
made a commit no slower in memory than the noise between two runs, and
2 to 3% slower on disk. The measuring found that two benchmarks of a
commit had failed since 2026-11-22 while the benchmark gate said ok;
both are mended, and the gate now fails on a benchmark that fails.
That and the rest it found are under
[What the measuring found](#what-the-measuring-found).

## The door for agents at the server, waiting, and files

`TestAgentsCampaign`, new in this release: one database on disk,
served by `fadodb serve` as it is told nothing but where its database
is; ap-agent's key, one caller on one connection, 200,000 calls a row.
Each row stands beside what it stands on, in the same run.

| Work | Throughput | p50 | p90 | p99 | max |
|---|---|---|---|---|---|
| read by id, a command at `/v1/` | 4,811/s | 0.203 ms | 0.237 ms | 0.353 ms | 13.8 ms |
| read by id, the tool `get` at `/mcp` | 4,629/s | 0.207 ms | 0.251 ms | 0.374 ms | 2.64 ms |
| transition, a command at `/v1/` | 2,943/s | 0.315 ms | 0.366 ms | 0.549 ms | 55.3 ms |
| transition, the tool `transition` at `/mcp` | 2,843/s | 0.322 ms | 0.383 ms | 0.588 ms | 53.5 ms |

- **A tool at `/mcp` costs what its command costs at `/v1/`**, and 4 to
  7 µs more at the median, 21 to 39 µs at p99: the message of the
  protocol around the command, read and written. One run.

Waiting for a change: a writer sends a move every millisecond, 5,000
of them, and each agent waits with `wait_for_changes` from the place it
was given, until it has had every move. How long after a move was sent
the agent has it:

| Agents | Moves heard | p50 | p90 | p99 | max |
|---|---|---|---|---|---|
| 1 | 5,000 | 0.490 ms | 0.599 ms | 0.870 ms | 19.3 ms |
| 100 | 500,000 | 33.15 ms | 93.84 ms | 322.2 ms | 646.9 ms |

- **One agent hears a move half a millisecond after it was sent**, the
  request of the move included.
- **A hundred agents fall behind** a writer that moves a document every
  millisecond. Each answer ends a request, so every move would have a
  hundred agents ask again: up to 100,000 requests a second, where this
  machine's server answers about 45,000 reads a second to sixteen
  callers. The agents take several moves in an answer as they fall
  behind, and hear all 5,000 in 13.7 s together, where one agent heard
  them in 5.4 s. The stream of changes holds a hundred subscribers
  behind the same writer at 2.67 ms at p99: [the stream](#the-stream).

Files of 1 MiB, each other bytes, 200 of them, sixteen at a time: the
door carries sixteen calls at once.

| Work | Took |
|---|---|
| put, `POST /v1/blobs`, sixteen callers | 232 ms, 864 MiB/s |
| `put_file`, through one door started with `--files` | 233 ms, 857 MiB/s |
| read, `GET /v1/file`, sixteen callers | 88 ms, 2,273 MiB/s |
| `get_file`, through one door started with `--files` | 95 ms, 2,105 MiB/s |

- **A file through the door moves as fast as through the server's own
  addresses**: the door reads the file from the folder as it sends it,
  and hashes what it writes as it comes, 7% slower than a caller that
  only reads it.

## What the measuring found

- **Two benchmarks of a commit failed, and the gate said ok.**
  `BenchmarkRecalculate`, the compute step of a commit, and
  `BenchmarkCommit`, a commit end to end, made an invoice whose customer
  is document 42 of a class they never defined. Since #191 on
  2026-11-22 a `ref` is checked when it is set (ADR-0076, item 11), so
  both failed from then on. The gate leaves out what one tree has and
  the other has not, and said ok on every pull request since, in CI and
  on this machine: `Recalculate` is in its set, and was compared with
  nothing. Both now define the customer before the invoice, as the
  tests do, and the gate fails when a benchmark fails in the tree it
  checks, or ran at the base and not there; one that fails only at the
  base is named. Every other benchmark of the repository was run once
  to find any other such: none.
- **The longest commit is two to five times v0.6.0's page**, and so is
  v0.6.0's own, built and run the same evening:
  [beside v0.6.0](#beside-v060-the-same-evening).
- **An act of a content administrator past the rules allocates twice
  more**: 172 against 170. Since the log of reads (#160), such a caller
  is asked the rules too, so that what it got past is written down
  (ADR-0067, item 1). Its time is that of the owner's own act, 54.8 µs
  against 54.0 µs.
- **Opening takes longer.** A database of 11.2 GB opens in 9.5 ms where
  it opened in 4.1 ms, and small databases in 0.5 to 1.8 ms more:
  [opening a database](#opening-a-database). Both are inside the
  budget; where the time goes was not measured.
- **The door an agent's program starts takes 0.53 ms to start, list its
  tools and end**, where v0.6.0 took 0.33 ms. Its list of tools grew
  from about 47,000 characters to about 74,000 with the commands of
  Phase 7; ADR-0064 still says 47,000.
- **The browser VM's size is checked by its own build**, which every
  push runs in CI and which fails past 102,400 bytes, and not by
  `scripts/sizegate.sh`, which ADR-0029 says gains the file.
- **The measuring itself.** It stopped once, at 19:15, for a check of a
  screen the owner was waiting for, and started again at 19:24; the
  campaign of rules and actions, twenty minutes in, ran again whole.
  The disk confirmed a write in 0.92 ms when the measuring began and in
  3.9 ms an hour later, which a commit does not wait for. ADR-0086 has
  no section on performance,
  which ADR-0012 asks every record to have.

## What is slow

- **A caller on this machine waits 0.3 ms for the server** where the
  Go API answers in 0.05 ms, and most of that is the machine's.
- **Callers that write at once wait for each other.** There is one
  writer at a time; sixteen get about 9,500 commits a second through
  the server between them, each waiting 1.5 ms.
- **A writer that never pauses waits now and then for the log to be
  emptied**: up to 190 to 440 ms this evening, in v0.6.0's build too.
- **A hundred agents that wait for every change fall behind** a writer
  that moves a document every millisecond: 33 ms at the median, 322 ms
  at p99. One agent waits 0.5 ms.
- **The stream falls behind a writer that never pauses** when a
  hundred subscribers listen: 13.2 ms at p99.
- **The flow of a class of a million documents takes four seconds**
  for a caller who reads them all.
- **Opening takes 0.65 ms a class**, and an open database of fifty
  classes holds 24 MB, and about 45 MB more once many callers have read
  from it at once, until it is closed.
- **Checking a password takes 60 ms of one core**, which is what it is
  for: a guess costs as much.
- **`MEDIAN` over a list costs 0.3 ms** among a million documents, the
  other figures about 0.2 ms.
