# v0.9.0: embedding, Phase 9

Measured on 2026-11-28 shortly after midnight on main at `719c704`, the
last pull request of the phase's steps, with Go 1.26.11, linux/amd64,
SQLite 1.62.0 and Python 3.14.4, on an Intel Core Ultra 9 275HX with 24
threads and 31 GB available to the Linux VM (WSL2, kernel 6.18), the
database files on the virtual disk that holds the home directory, ext4
on a VHD on NVMe. An fsync of 4 KB cost 4.55 ms at the median when the
campaign began and 3.81 ms when it ended; a commit does not wait for the
disk unless the database was created with `FULL`. Each way to a database
ran three times on databases of its own, each run five rounds of 2,000
reads of one document and 2,000 documents made, and a run's figure is
the median of its rounds. Other programs of the machine ran meanwhile, a
load of 1.5 to 2.3 on its 24 threads.

Phase 9 sets no budget: every row here is published, for the reader to
weigh. This page holds what Phase 9 adds, the ways into a database from
a program of another language
([ADR-0101](../adr/0101-the-library-of-c.md),
[ADR-0102](../adr/0102-the-programs-own-actions-and-the-library-with-duckdb.md)).

## What one command costs, on each way to a database

A read is `get` of one document by its id, and a document made is
`create` of a new one, as Ann.

| Way | A read, µs, three runs | A document made, µs, three runs |
|---|---|---|
| Go, the API (`db.Get`, `db.Create`) | 5.8, 5.8, 6.0 | 66.5, 67.2, 67.9 |
| Go, the command set (`db.Exec`) | 6.3, 7.1, 6.9 | 70.2, 71.7, 72.1 |
| Go, the library's own code, without C | 10.0, 10.0, 10.1 | 78.2, 79.4, 78.2 |
| C, the library (`fado_exec`) | 10.8, 10.5, 10.6 | 83.7, 78.9, 80.0 |
| Python, in the same process (`fadodb.open`) | 18.0, 16.0, 15.5 | 99.3, 92.9, 92.6 |
| Python, over HTTP to `fadodb-core serve` on this machine (`fadodb.connect`) | 599.7, 594.5, 597.6 | 743.7, 739.9, 744.4 |
| Python, over HTTP with one connection kept open (`http.client`, not the client) | 345.9, 346.1, 347.6 | 504.2, 486.5, 488.0 |

In words: a program of C reads a document through the library in about
11 µs, twice what the Go API takes, and a program of Python in about 16
µs. A document made costs about 80 µs from C and 95 from Python, against
67 in Go: the commit is most of it. Over HTTP the same read costs a
little under 0.6 ms from Python, of which a quarter of a millisecond is
the connection the client opens for every command.

## What the measuring found

1. **The library adds 3 to 4 µs to a read before C is crossed, and C
   itself half a microsecond.** Of those microseconds, reading the
   caller's JSON on every call is 1.3 µs and 37 allocations, measured
   alone; the rest is not yet accounted for. A program that calls as
   the same caller again and again could be spared the reading. Not
   done: a read in 11 µs is no hindrance, and the reason for the rest
   should be found first.
2. **The Python client opens a connection for every command over
   HTTP**, as Python's `urllib` does: a connection kept open would save
   about a quarter of a millisecond a command. It needs a rule for a
   command whose kept connection the server had closed while it was
   idle, which the client may send again by itself only when the command
   carries a key. Not done.
3. **The wheel for macOS carries DuckDB's library whole**, one file of
   134 MB for both kinds of machine, so it is the largest of the wheels.
   A pull request does not keep the wheels, so its size is not measured
   here; the release's list of files gives it.

## How to run it

The campaign of the library runs in its own module, with a C compiler,
Python and the databases on a disk:

```
cd cabi && FADODB_BENCH=library FADODB_BENCH_DIR=/path/on/disk CGO_ENABLED=1 go test -count=1 -v -run TestLibraryCampaign .
```

It builds `libfadodb-core`, `testdata/measure.c` against it and
`fadodb-core`, and runs `clients/py/measure.py` for the ways of Python.
The sizes are what `scripts/library.sh build` and `pack` print.
